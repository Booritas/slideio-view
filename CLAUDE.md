This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

SlideIO Viewer is a cross-platform C++ desktop application for viewing, navigating, and annotating digital pathology whole-slide images (WSI). It uses the **SlideIO library** for reading image data and **Qt 6** for the UI.

**Current state:** Implemented and building. The four layer libraries, the Qt application, a CMake/Conan build and four ctest suites all exist under `src/` and `tests/`. The viewer opens slides, navigates a tile pyramid on OpenGL, manages ICC colour profiles, and supports rectangle, polygon and freehand-line annotations (draw, select, move, delete) that **persist to disk** — one JSON file per (slide, scene) in a workspace folder under Documents, autosaved and reloaded when the slide reopens.

Annotation persistence is **in regular use and its documented checks are covered** as of 2026-10-13 — see item 0 of `docs/superpowers/specs/2026-10-11-annotation-persistence-followups.md`, which records what was verified and how. That item is now the list to re-run when this area changes, not a backlog.

**No test suite creates a `QApplication`**, so no widget can be constructed in a test and nothing in `ViewportWidget` is reachable from any suite. That is why a manual list exists at all. It also means a claim about runtime behaviour in this file is only as good as the last time somebody ran it: **do not infer from silence here that a path has never been exercised** — earlier drafts of this file and of item 0 did exactly that, asserted the subsystem had never been run, and were wrong. Ask the project owner, who tests this application regularly.

**Minor review findings that were raised but not acted on are indexed in `docs/superpowers/specs/2026-10-19-deferred-findings.md`** — 117 of them, from fourteen rounds, recovered only as each finding's opening clause: the ledgers they lived in were under `.superpowers/sdd/`, which is gitignored and now empty. **Append new deferred findings to that tracked file, not only to a round's ledger** — a finding nobody acted on still has to survive a `git clone`. They were split into seven batches by area and **all seven were worked on 2026-10-19/20: 117 triaged, 27 fixed, 23 stems too truncated to act on.** That count was one short until 2026-10-20 — entry 66 carried no verdict at all and nothing caught it, because the tally was kept by hand; a one-line awk check — any numbered line carrying no bracketed verdict — is what found it, and it now stands at the top of that file. Three lessons are worth keeping. **A fix cannot land on one side of a layer boundary when both sides compare the same strings** — entry 72 was the core half of entry 106, and fixing 106 alone left `ui::categoryTally` folding case with Qt while `core::normalizeCategoryList` and `core::retagClassification` folded ASCII-only, so a category typed once with an umlaut and once in capitals was one row of eight in the tally and two entries in the vocabulary, and renaming it changed five of the eight. `core::caseFoldKey` is the single fold now — ASCII, Latin-1 Supplement, Latin Extended-A, Greek and Cyrillic over UTF-8 bytes; everything else passes through — and ui calls it instead of Qt, deliberately narrower than Qt so the two layers agree. **The fold is only ever a comparison key**, never stored or displayed: `normalizeCategoryList` keeps the trimmed original, `categoryTally` rows carry the spelling first seen, `retagClassification` writes the target as typed. So a narrow fold costs nothing but whether two differently-CASED spellings are judged one category, and the boundary that matters is not Latin but **bicameral** — Chinese, Japanese, Korean, Arabic, Hebrew, Thai and Devanagari have no case, so folding them to themselves is what caseless matching means for them, in Qt too. Greek and Cyrillic were added 2026-10-20 when that trade-off was questioned; Armenian, Georgian, archaic Greek and the Turkish dotless i are still not folded and a test pins that boundary. **Two sweeps walk every codepoint from U+00C0 to U+04FF** asserting the fold is idempotent and maps one codepoint to one codepoint: every range bound and parity rule in the three script blocks is an off-by-one away from mapping a lowercase letter onto a different letter, and the sweep is what catches it. Keep them when extending the fold. `std::tolower` and `std::isspace` are gone from both files — they read the global C locale, and under a single-byte one they rewrite or trim the lead byte of a UTF-8 letter. **A signal everyone connects by default is the thing that is wrong**: `AnnotationModel::setGeometry` now emits `annotationGeometryChanged` rather than `annotationChanged`, because a move-drag emits one per mouse move and `AnnotationListPanel` rebuilt its whole tree on each — several hundred `QTreeWidgetItem`s per frame to produce rows identical to the ones on screen, since a row shows a label, a type and a classification and `core::typeOf` is derived from the variant alternative a translate keeps. The viewport, the properties panel and `AnnotationPersistenceService` each connect it and say why; the list panel is the one that does not. **And most of the index was already closed** — in B2 and B3, fifteen of nineteen entries were fixed by later rounds that never struck them off, seven of them by a comment standing exactly where the finding pointed. ## Architecture

**Layered, strict downward dependency.** Components in _italics_ are designed but not built.

```
Presentation (Qt UI)   →  MainWindow, ViewportWidget, PreferencesDialog,
                          AnnotationSettings, Panels, dialogs                  (34 .cpp)
Application (Services) →  AnnotationModel, AnnotationPersistenceService,
                          UndoRedoStack, AnnotationEditCommand, AnnotationEditing,
                          AnnotationRetagCommand,
                          WorkspaceSwitch, SlideViewerService, _CaseService_    (8 .cpp)
Domain (Core Logic)    →  Annotation, AnnotationSerialization, AutosavePolicy,
                          Iso8601, Viewport, TilePyramid, CoordinateSystem,
                          AnnotationMeasurement, AnnotationMerge,
                          WorkspaceSwitchPolicy, LevelRaster,
                          AnnotationCategories                                 (24 .cpp)
Infrastructure         →  SlideIOAdapter, LruTileCache, TileLoadScheduler,
                          JsonAnnotationRepository,
                          QSettingsColorProfileOverrideStore, _RemoteClient_    (6 .cpp)
```

- Core is **pure C++17, Qt-free** — enforced by it linking no Qt target at all. Anything needing `QUuid`, `QSettings` or signals belongs one layer up. It links `nlohmann_json` PRIVATE, so JSON appears in no core public header.
- Infrastructure implements core interfaces (`ISlideSource`, `ITileCache`, `IAnnotationRepository`).
- SlideIO access is isolated behind `SlideIOAdapter`. There is **no** `SlideIOAdapterPool` — one shared scene serves all tile workers; see the project memory on scene sharing.

Qt6::Network is still unused.

## Coding Conventions

```
Classes/Structs:    PascalCase          (TileCache, AnnotationModel)
Functions/Methods:  camelCase           (readTile, setZoomLevel)
Member variables:   m_camelCase         (m_memoryBudget, m_tileCache)
Constants:          kPascalCase         (kDefaultTileSize, kMaxZoomLevel)
Enums:              PascalCase::Value   (AnnotationType::Polygon)
Namespaces:         lowercase           (slideio::viewer::core)
Files:              PascalCase.h/.cpp   (TileCache.h, TileCache.cpp)
```

- 4-space indent, 120-char line limit
- Allman braces for classes/functions, K&R for control flow
- `#pragma once` for header guards
- Include order: own header, project headers, Qt headers, std headers
- PIMPL idiom for Qt widget classes

## Build and Test

```bash
cmake --build build/build --config Release
ctest --test-dir build/build -C Release --output-on-failure
cmake --install build/build --config Release
```

**Never run a Qt-linked test executable directly.** `app-tests`, `infra-tests` and `ui-tests` find their DLLs through a ctest `ENVIRONMENT_MODIFICATION` property that only applies under `ctest`; running the `.exe` pops a modal Windows error box that blocks until a human dismisses it. Only `core-tests` is safe to run directly.

The build-tree executable will not start either — install first and run `build/install/release/bin/slideio-viewer.exe`.

**A running viewer silently turns `cmake --install` into a no-op.** Windows locks the running `.exe`, so the copy is skipped, the command still exits 0, and the installed binary stays at the previous build. Everything measured afterwards is the old code. Kill the viewer before installing. When a change has to be in the binary you are about to drive, confirm it is rather than assuming: compare the timestamps of `build/install/release/bin/slideio-viewer.exe` and `build/build/Release/slideio-viewer.exe`, or grep the installed binary for a string the change introduces. `ctest` after a failed build has the same shape — the suites run whatever binaries are already there and report green. **Both failures look exactly like success, so the exit code is not the thing to check; the artifact is.**

No test binary creates a `QApplication`, so **no test may construct a widget**. Logic that needs testing is extracted into pure functions over plain data; see `ColorProfilePolicy`, `AnnotationInteraction`, `DriverFilters`.

## Key Design Decisions

Shipped:

- **Content-derived slide IDs** — `core::computeSlideId`, FNV-1a over file size and per-scene geometry. Keys the per-slide ICC profile store. Not cryptographic.
- **Annotation files are keyed by (slide ID, scene index)**, not the slide ID alone — `<slideId>.s<N>.annotations.json`. `computeSlideId` is file-level by construction, but annotations live in one scene's coordinate space, so keying on the ID alone would load a multi-scene file's scene 0 annotations against scene 1's coordinates.
- **`schemaVersion` does not move when a geometry type is added.** A higher version is refused outright, so bumping it would make every shipped build refuse rectangle-only files during a staggered rollout. An old build meeting a new shape is designed to fail on that shape alone, name it, and leave the file intact; **observed 2026-10-12** (check P14) — a pre-branch build shown a polygon file refused it with `unknown geometry type 'polygon'` and left every byte unchanged.
- **A file we could not parse is never a file we write to.** A load failure or an unresolved slide-ID mismatch leaves `AnnotationPersistenceService` inactive, and an inactive service never writes. The serializer refuses anything the parser would reject, so the application cannot write a file it cannot read back.
- **`closeSlide()` flushes before it resets.** `endSlide()` is its first statement, ahead of `resetAnnotationState()`. Since `openScene()` and `reopenCurrentScene()` both route through `closeSlide()`, that one ordering is what makes annotations survive a slide switch and an ICC profile change. Do not move it into a `slideClosed` handler — that fires after the model is already empty.
- **Annotation geometry** uses `std::variant` over `RectangleGeometry`, `PolygonGeometry` and `EllipseGeometry`, with free functions — `boundingBox`, `hitTest`, `typeOf`, `outline`, `translated`, `hasWellDefinedArea` — dispatching by `std::visit`. One `PolygonGeometry` covers both the closed polygon and the open freehand line; they differ only in a `closed` flag. `PointGeometry` and `ArrowGeometry` are separate alternatives rather than degenerate cases of those: a marker is not a zero-extent rectangle, and an arrow cannot be a two-vertex polyline because `typeOf()` derives the type from the geometry and the two would be indistinguishable. **An arrow's endpoint pair is ORDERED** — `tail` then `head` — and must never be normalised the way a rectangle's corners are, or every arrow drawn right-to-left silently reverses. Adding a shape means adding an overload to each of those six, plus one to every other exhaustive `std::visit` over the variant. **Adding the ellipse in 2026-10 fired ten such sites**, of which the design spec had enumerated five: the six in `AnnotationGeometry.cpp`, then `shapeToJson`, `isRepresentableShape` and `geometryTypeName`'s `static_assert` in `AnnotationSerialization.cpp`, and `ShapeNameVisitor` in `src/ui/src/AnnotationShapeName.cpp` — which also has a `switch` over `AnnotationType` beside it. **Adding the point and arrow a day later fired twelve**: those eleven — counting `ShapeNameVisitor` and the `AnnotationType` switch beside it separately — plus `replaceBox` in `BoxResize.cpp`, which box resizing had added in between. That twelfth is the first demonstration that `withBoxReplaced`'s `std::visit` earns what it costs: both new types were forced to answer `std::nullopt` where a `get_if` chain would have let them fall silently through to "not resizable". **The next shape will fire thirteen** — `decorationFor` in `AnnotationDecoration.cpp` is a new one, deliberately a visited overload set rather than a `get_if` chain for the same reason. Do not trust a count; let the compiler enumerate them. None of these can be forgotten silently: each missing overload is a compile error naming the site. **One site is the exception:** `readGeometry` in `AnnotationSerialization.cpp` is a string-comparison chain with no compile-time link to the variant, so it must be remembered by hand. Forget its branch and the application writes files it then refuses to open, breaking the "never write a file we cannot read back" invariant. A new geometry type must therefore land with a serializer round-trip test, because nothing else forces its reader branch to exist. The `static_assert` guards that once forced the five geometry-dispatch sites are gone — those are real overload dispatch now. **One `static_assert` remains**, in `geometryTypeName` (`AnnotationSerialization.cpp:206`), and it is one of the twelve sites above.
- **An ellipse is its inscribed 512-gon.** `EllipseGeometry` stores a bounding box; `outline()` expands it into `kEllipseOutlineVertices` points, and the painter, `hitTest` and `measure` all read that one outline, so they cannot disagree. The count is fixed and never adaptive: an adaptive one would make a stored annotation's measured area depend on the zoom it was measured at. The area therefore reads about 0.0025% under the true ellipse — deterministic, documented, and far inside the scanner's own calibration uncertainty. `core::measure()` short-circuits `isSelfIntersecting` for any shape `hasWellDefinedArea` accepts: at 512 vertices that test costs ~131k segment-pair comparisons, and on a *degenerate* ellipse its collinear-overlap rule would otherwise withhold an area that is plainly zero — so skipping it is more correct, not merely cheaper. **That predicate is named for what it promises.** It was `isConvexByConstruction`, then nearly `cannotSelfIntersect`; both were false for a degenerate ellipse or zero-extent rectangle, which are collinear and whose generated vertices do overlap. Only the area claim survives those inputs. Do not reach for it to justify a convex-hull or point-in-convex-polygon shortcut. See `docs/superpowers/specs/2026-10-16-annotation-ellipse-design.md` §3.

- **Vertex editing is a mode, and it addresses STORED vertices.** Double-clicking a committed polygon or freehand line enters it; Escape, a press off the shape, a tool change or a slide close leaves it. While it is on, `ViewportWidget` paints a handle per vertex and routes presses through `ui::resolveVertexEditPress` — except under held space, which still pans, because that promise predates the mode. Every operation — `core::nearestVertex`, `nearestEdge`, `withVertexMoved`, `withVertexInserted`, `withVertexRemoved` — indexes `poly.vertices` and **never** `core::outline()`, which drops consecutive duplicates and so does not address stored vertices; every polygon saved before 2026-10-17 carries such a duplicate. These take `PolygonGeometry` directly rather than the variant, which is why adding them fired none of the ten dispatch sites. Removal refuses below the serializer's own minimum, so the tool cannot build a shape the format would reject. One completed gesture is one undo step, and `core::sameVertices` — not `ui::moveEdit`, which compares bounding boxes and is blind to an interior vertex moving inside an unchanged extent — decides whether anything changed. See `docs/superpowers/specs/2026-10-17-annotation-vertex-editing-design.md`.

- **Box resize handles are live on selection, with no mode.** A selected `RectangleGeometry` or `EllipseGeometry` paints eight handles — four corners, four edge midpoints — and a press on one starts a resize, tested *before* `resolveDragOwner` because a corner handle sits on the outline and would otherwise be taken as a move. No mode, deliberately: the vertex-editing mode exists only because 400 handles would bury a trace, and eight cannot. The core operations take a plain `RectF`, so the same four functions resize a rectangle and an ellipse; only `core::withBoxReplaced` touches the variant, and it uses `std::visit` rather than `get_if` so a future box-shaped type is a compile error rather than a silent "not resizable". Dragging a handle past its opposite edge flips the box, as a creation drag may, and `withMinimumExtent` widens a collapsed axis at commit. **Six exits record the undo step** — release, focus loss, Escape, undo mid-drag, tool change and slide close — all through `recordBoxResize()`; vertex editing found that list one review at a time and this one was written from it. Note two of the six are traps the surrounding code sets: `endToolDrag()` returns early unless `dragOwner == Tool`, and `resetAnnotationState()` must clear the new members or an annotation from one slide is restored onto the next. Twenty-three manual checks were run against this build — group AA, 23/23, recorded in `docs/superpowers/specs/2026-10-17-annotation-box-resize-design.md` §7.3 along with how a read-only slide is produced for a manual check. **A drag moves the handle BY the press delta, not TO the cursor** (`core::withBoxHandleDragged`): a press lands anywhere within `nearestBoxHandle`'s six-pixel tolerance, there is no drag threshold on this path, and handing the raw cursor to `withBoxHandleAt` snapped the edge across that offset on the first mouse-move — committing a resize, an undo step and an autosave for what the user read as a click. Group AA did not catch it and neither did two reviews; an independent review of the whole branch did, 2026-10-18.

- **A marker and an arrowhead are sized in screen pixels, by core.** `core::screenDecoration` (`AnnotationDecoration.{h,cpp}`) answers, for one geometry, what glyph it needs and how many pixels across — a `Disc` whose size is a radius, an `ArrowHead` whose size is its length along the shaft, or nothing at all. The painter is told a kind, an anchor in slide units and a pixel size, and still has no idea what shape it is drawing; it derives the head's direction from the two shaft points it has already converted, which is correct because the viewport only pans and zooms. **The disc radius is a parameter, not a core constant:** `kHitToleranceScreenPixels` lives in ui and core cannot reach it, so `ViewportWidget` passes the same value it passes to the hit test and the marker you see is the target you click by construction. The arrowhead's two constants go the other way and live in core, because the arithmetic that reads them is there — the head is the smaller of `kArrowHeadScreenPixels` and `kArrowHeadMaxShaftFraction` of the shaft, since fixed alone outgrows a short arrow and proportional alone disappears. The rejected alternative was making `outline()` take a scale, which the ellipse spec forbids: a stored annotation's measured value would then depend on the zoom it happened to be measured at. A selected marker is **ringed** rather than outlined, because a point's outline is one vertex and the ordinary selection stroke paints nothing at all. Twenty-three manual checks were run against this build — group AB, 23/23, with AB19 and AB23 answered by the layers in front of the gate they name rather than by that gate, which no UI route reaches — and recorded in `docs/superpowers/specs/2026-10-17-annotation-point-arrow-design.md` §7.3 along with the measured glyph sizes and the one defect they found.

- **Every path that creates an annotation asks `annotationsEditable()` first.** `commitPendingShape` has since persistence landed; `commitDrawDrag` did not until 2026-10-17, so the rectangle and ellipse tools were creating a shape on a read-only slide in silence. **Nothing in the UI can reach it today**, and the 2026-10-17 claim that it could was wrong: a read-only slide disables the drawing tool *actions*, and `applyAnnotationAvailability` also calls `setActiveTool(Pan)` whenever a real gate applies (`MainWindow.cpp:1770`). Since the persistence service only changes `m_active` in `beginSlide`/`endSlide`, every transition into non-editable is also a transition to the Pan tool, so there is no way to hold a drawing tool over a slide that refuses edits. The gate stays as defence in depth behind those two layers — group AB19 and AB23 found this by failing to set the check up (spec §7.3), and that spec now names all three layers so nobody re-attempts it: the six tool actions are disabled (`MainWindow.cpp:1766-1771`), a disabled `QAction` is removed from Qt's shortcut map so the bare-letter keys die with them, and arming the tool beforehand is closed by `setActiveTool(Pan)` at `MainWindow.cpp:1797`. The refusal is noisy (`annotationEditBlocked`) where a misclick is silent: a gesture too small to be a shape is the user's own doing, and a gesture refused by the slide is not.

- **Categorized counting uses `classification`, not a second axis.** The counting category **is** `core::AnnotationProperties::classification`, so the file format and `schemaVersion` are untouched and `AnnotationSerialization.cpp` was not modified at all in this round. The rejected alternative, a separate `category` field, would have been silently dropped by an older build on rewrite. The current category is stamped in `AnnotationModel::add()` (`AnnotationModel.cpp:42-45`), keyed on `core::typeOf(geometry) == Point` and **not** on the active tool, because the model does not know about tools and because app-tests can construct a model while nothing can construct a `ViewportWidget`. Every rule that could be tested was pushed down to where a test reaches it: `core::normalizeCategoryList`, `core::retagClassification`, `core::isUnclassifiedCategory` (`AnnotationCategories.cpp:30-88`) and `ui::categoryTally`. The round proved why: the one rule left to a caller, refusing an empty rename target, turned out to be a bulk-unclassify waiting to happen, and was moved into core. `ui::categoryTally` never orders rows by count and never sees the filter text (`AnnotationListPolicy.h:85-98`): a row that moves while the user is clicking at it is a misclick in a several-hundred-click workflow, and a clinical count that changed when someone typed in a search box would be a trap. "Unclassified" is the absence of a value and can never be a configured category, a rename source or a rename target; `core::isUnclassifiedCategory` is the single predicate (also applied by `AnnotationModel::setCurrentCategory` and the properties panel's Classification edit, so it cannot be written either), and `CategoryTallyRow::synthetic` is how the panel identifies the row without comparing a translatable label (`AnnotationListPanel.cpp:130-132`). **The category list is a global preference and is deliberately not on the undo stack** (`MainWindow.cpp:2113-2116`): the undo stack is per-slide and cleared on a slide change, while the vocabulary is shared across slides, so undoing on one slide must not revert a change another slide is using. A rename therefore undoes its annotation changes but not its vocabulary change. **That same globalness is why a rename is not one gate but three states** — `ui::categoryRenameScope`, 2026-10-20, closing deferred entries 66 and 67. The gate used to ask `AnnotationPersistenceService::isActive()` alone, which is false BOTH for a slide whose annotation file could not be parsed AND for no slide at all, so renaming a category on an empty viewer answered "These annotations are open read-only and cannot be changed" and named a slide the user did not have. With nothing open the rename is a preference edit with nothing to retag and goes through; with a slide open that refuses the retag it is still refused, because renaming the vocabulary half alone would leave the annotations on screen carrying the old word and the tally would show the new name at zero beside an unconfigured row holding the real count — on every other slide too. **Remove from list, beside it in the same context menu, has never been gated at all, and that asymmetry is what showed the gate was in the wrong place rather than merely wrongly worded.** `ui::categoryRenameScope` is tested; the wiring that asks it is not and cannot be, so the no-slide path was run by hand against the built viewer on 2026-10-20 and passed — recorded as **AC31**, which took group AC to 31 of 31. **The counting combo refuses the keys that would step it.** `ui::countingComboSwallowsKey` and `ui::countingComboSwallowsWheel` swallow Up, Down, PageUp, PageDown and the wheel while the dropdown is CLOSED, through an event filter on the combo and its line edit. A closed editable `QComboBox` treats those as "step to the next item" and replaces the text, which here silently reassigns the clinical counting category — group AC26 typed a category, counted a marker under it, pressed Down, and every later click was counted under a different one with nothing announcing the change. The user of a several-hundred-click pass reads the slide and the tally, not the combo, and the tally agrees with the mistake because it is correct about what was stored. Only the accident is removed: with the popup open the same keys move a highlight and commit nothing, so F4-arrows-Enter still picks a category deliberately. Thirty manual checks were run against this build — group AC, **30 of 30 pass**, with AC31 added and run 2026-10-20 for the rename-with-nothing-open path (**31 of 31**), recorded in the spec's §7.5, two of them against a clause struck on 2026-10-19 rather than satisfied. **Creating an annotation selects it**, so the list scrolls to the new row and drops whatever the user had selected; a counting pass is several hundred creations and the list moves on every one. AC9 demanded the opposite and read as a failure until the project owner confirmed the list should follow the annotation just placed. **The tally is a read-out, not a control** (`NoSelection` + `Qt::NoFocus`, `AnnotationListPanel.cpp:81-82`), which is what AC29's Menu-key clause demanded be otherwise. Keep it that way: the bare-letter tool shortcuts `V R E O F M A` are `Qt::WidgetWithChildrenShortcut` scoped to the viewport (`MainWindow.cpp:416-422`), so `NoFocus` is the only reason clicking a tally row — including right-clicking it for its context menu — does not stop `M` placing markers; `rebuild()` calls `tally->clear()` on every annotation change, which would destroy a selection on every single marker; and the menu already resolves its row by `itemAt(at)`, so a selection would give it a second, disagreeing candidate. A selectable tally earns its cost only if selecting a row *sets the counting category* — a feature to specify, not a side effect of making a read-out focusable. Both struck clauses belong to the same class as AB19 and AB23: a manual check that asserts an intention the code deliberately does not have. **Writing the check list before the implementation is what makes this class appear** — it is the cost of the practice, not a defect in it, and the right response is to strike the check with its reasons recorded rather than leave it looking like an open failure. AC25 earned its place: clearing the list writes an empty `String[]` to the real registry backend and survives a restart without the five defaults creeping back, which only the INI backend had ever shown. Three cosmetic defects surfaced and were fixed on 2026-10-19, each with a different cause and none of them where the symptom pointed. **The window title kept naming a slide after Ctrl+W closed it** — which made a correctly closed viewer look like a failed reopen for a whole session. It is cleared from the Close action and from the failed-open handler, deliberately **not** from `slideClosed`, which also fires at the start of every open: `openSlide` sets the title before the viewport closes the previous slide, so clearing there would blank it on every open instead of only on a close. **The Scenes panel did not repopulate after a close-and-reopen** because the Close action emptied both panels but left `lastOpenedFilePath` naming the file it had just emptied them of, and the `slideOpened` handler skips the rebuild when the file has not changed; the memo now clears beside the panels, so it always names the file they hold. **Recent Files listed one slide twice** because the shell's backslashes (`main.cpp` passes `argv[1]` through unchanged) and the file dialog's forward slashes are two spellings an exact `removeAll` does not reconcile, while the menu labels an entry with its last component alone. That rule now lives in `ui::recentFilesWithPathPromoted`, which normalizes stored entries as it rewrites them — so a list already holding both spellings repairs itself without a migration — and folds separators and case **only on Windows**, because on a case-sensitive platform a backslash is an ordinary file-name character and folding either would rewrite a stored path into one that no longer opens. See `docs/superpowers/specs/2026-10-18-annotation-categorized-counting-design.md`.
- **The counts export is the strip, not a second count of it.** `File > Export Counts...` (2026-10-20) writes one CSV per scene, and `MainWindow::Impl::exportCounts` builds its rows with the **same `ui::categoryTally` call on the same two inputs** the counting strip uses — a report that could drift from the screen it was read off is a clinical trap, and the file is the copy that gets filed. `ui::categoryCountCsv` and `ui::countExportFileStem` (`AnnotationCountExport.{h,cpp}`, 19 tests) hold every formatting decision, because the action, the dialog and the write are unreachable from any suite and a rule inside the lambda is a rule nothing would check. The file is UTF-8 **with a byte-order mark** — without it Excel reads a `.csv` in the machine's legacy codepage, and with Greek and Cyrillic now folded a non-ASCII category is an ordinary thing to have — CRLF per RFC 4180, with **provenance repeated on every row** (`slide`, `scene`, `slide_id`, `exported_at`) so two exports paste one under the other and every row still says what it counted; a header block would have to be a comment, which is the one thing CSV has no agreed syntax for. **Order is the tally's**, never by count, for the same reason the strip is not: a row that moves under a clicking hand is a misclick. **No total row** — every annotation lands in exactly one row so the column already sums to the scene's annotation count, and a total line is the classic thing that silently becomes a data row on re-read. **A field a spreadsheet would evaluate gets a leading apostrophe**: a category is whatever the user typed, Excel, LibreOffice and Sheets all evaluate a cell beginning `=`, `+`, `-` or `@`, and **RFC 4180 quoting does not prevent evaluation**; a category genuinely named `-Tumor` therefore reads back with an apostrophe, which is the deliberate side of that trade. The write does `flush()` and `close()` explicitly and checks the byte count, because `~QFile` cannot report a failure and a counts file short by a row reads as a complete count. **The action is gated on a slide being OPEN, not on annotations being editable**, so it is absent from `applyAnnotationAvailability` and paired with `closeAction` at all four of its sites: a read-only slide's counts are exactly what a reader opening one wants, which is why the tally stays visible there too. Seventeen manual checks were run 2026-10-21 — group AD, **17 of 17 pass**, recorded in `docs/superpowers/specs/2026-10-20-annotation-count-export-design.md` §6 — with two caveats that are not failures. **AD3, AD6 and AD8 ran in LibreOffice Calc**, the test machine having no Excel, so they stay open for Excel itself; and Calc's import does not evaluate formulas by default, so its run cannot show that the apostrophe is what stops one. **AD14 cannot be reached through a read-only folder on Windows**: the native save dialog refuses the folder before `exportCounts` sees the path, so the application's own write-failure warning was reached through an existing file with write denied.
- **The GeoJSON export is the screen's shapes in QuPath's vocabulary.** `File > Export Annotations as GeoJSON...` (2026-10-21, FR-ANN-34's GeoJSON half) writes one `FeatureCollection` per scene through the pure `core::annotationsToGeoJson` (`AnnotationGeoJson.{h,cpp}`, 24 tests). **Every shape is written from `core::outline()`**, the one point sequence the painter, the hit test and `measure()` read, so the file cannot disagree with the screen: an ellipse is its 513-position ring, an arrow a two-point `LineString` tail first, an open trace a `LineString`; rings are closed, winding is as drawn and a self-intersecting trace is written as it is. Coordinates are level-0 pixels of the scene untransformed — QuPath's own space, so there is no transform to get wrong. **The QuPath field names were read out of `qupath-core-0.7.0.jar`**, not recalled: `objectType`, `id`, `name`, `color`, `classification {name, color}`. An unclassified annotation — blank, or "Unclassified" in any case, the tally's own rule — carries no `classification`, because QuPath shows a class literally called Unclassified as a real one. Everything QuPath has no field for (type, notes, author, timestamps, line width, fill opacity, `#RRGGBBAA`) goes under one `slideio` key per feature, and the collection's `slideio` member carries provenance and `pixelSizeMicrons` only when known. The file is compact, UTF-8 without BOM, and dumped with nlohmann's `error_handler_t::replace`: annotation files are hand-editable and the default handler throws on invalid UTF-8. **Gated and written exactly as Export Counts is** — every `exportCountsAction->setEnabled` has an `exportAnnotationsAction` twin, every annotation in the model and never the filtered list, the same Truncate/byte-count/flush write — and the export is built before the dialog so an unwritable scene is reported without first asking where to put it. Its `GeometryVisitor` is one more exhaustive dispatch site a new shape must answer. Fifteen manual checks were run 2026-10-21 — group AF, **15 of 15 pass**, recorded in `docs/superpowers/specs/2026-10-21-annotation-geojson-export-design.md` §7 — with QuPath checked through its own reader (`PathIO.readObjects` under `QuPath-0.7.0 (console).exe script`), which compares coordinates as numbers but does not exercise QuPath's GUI import.
  **The GeoJSON import adds, and says what it will add before it does.** `File > Import Annotations from GeoJSON...` (2026-10-22, FR-ANN-33's GeoJSON half) reads through the pure `core::geoJsonToAnnotations` (beside the writer in `AnnotationGeoJson.{h,cpp}`), which accepts a FeatureCollection, a Feature or an array of them and accounts for every feature: imported, or counted under one reason — a non-annotation `objectType` (detections, cells), holes, an unsupported or invalid geometry — so `featuresRead == featuresImported + every skip count`. A feature carrying the export's `slideio` block whose type fits its geometry comes back exactly, ellipse and arrow included; **the geometry wins any disagreement**. A MultiPoint becomes one marker per position, because QuPath writes a whole Points class as one; **part *i* of a multi-part feature takes the feature id plus `#i`**, never a fresh id, or a second import of one Points class adds all but its first point again. The reader never copies the parsed document and never recurses over its depth — nlohmann's copy is recursive, and a file nested 20 000 levels deep crashed it until the final review caught it. Core cannot mint UUIDs, so it leaves an id empty and `app::planImport` fills it; **an id the scene already holds is skipped, not duplicated**, which is what keeps a second import of one file from doubling a clinical count. One `QMessageBox` built by the pure `ui::geoJsonImportSummary` shows the counts and warns when the file names another slide or scene or its shapes lie wholly off this one; neither warning refuses. The commit is one `AnnotationModel::insertMany` — one `annotationsBulkChanged`, so one list rebuild and the existing autosave — recorded as one `app::AnnotationImportCommand`, whose undo is `removeMany` of exactly the ids it added. **Gated with the drawing tools in `applyAnnotationAvailability`, not with the exports**: it is the one menu action that creates annotations. Coordinate positions are counted, not de-duplicated, against the serializer's vertex minimums, so a degenerate polygon this viewer exported imports back. A `1e999` literal makes nlohmann refuse the whole file, not one feature. Twelve manual checks were run 2026-10-22 — group AG, **12 of 12 pass**, recorded in `docs/superpowers/specs/2026-10-22-annotation-geojson-import-design.md` §6 — with the QuPath fixture written by QuPath's own `PathIO.exportObjectsAsGeoJSON` from a console script, and AG1's associated-image clause struck as unreachable from the UI.
  **Both exports refuse a scene whose annotations were not loaded** (`AnnotationPersistenceService::annotationsLoaded()`, 2026-10-21, found by the whole-branch review): after a load failure, on an associated image or an unidentified slide, or with a mismatch resolved by ignoring the stored annotations, the model is empty without the scene being empty, and both exports used to file a complete-looking false zero — a valid empty FeatureCollection, a counts file of zeros. A scene locked by another instance or opened read-only after a mismatch IS loaded and stays exportable.
- **The annotation file is locked while a scene is open, and the lock is held EXACTLY while the service may write.** FR-ANN-32, 2026-10-20. Until then two instances with one slide open were last-writer-wins in silence: both load, both autosave every two seconds, and the second write erases the first with no error and nothing in the log. `infra::JsonAnnotationRepository::lock()` takes a `QLockFile` on `<slideId>.s<N>.annotations.json.lock` — Qt's convention of the guarded name plus `.lock` — **keyed by (slide, scene) like the file itself**, because a lock on the slide alone would lock a colleague out of every other scene of a multi-scene slide. It is taken in `beginSlide` **before the load**, since the lock is about the key and not about what turned out to be in the file. `AnnotationPersistenceService::setActive(false)` releases it, which is what makes "held exactly while writable" structural instead of something each of the half-dozen sites that turn writing off has to remember — so a slide that went read-only for any other reason gives the lock straight back rather than locking out an instance that might repair it. **Contention is not a load failure:** the annotations load and show, only `isActive()` goes false, and the whole existing read-only path applies. `ViewportWidget` picks between two reasons, because the user can act on "another window has this open" and cannot act on "the stored file could not be used", and reporting the second for the first sends somebody looking for a corrupt file that is fine. **Three things are deliberate and easy to get wrong later.** `tryLock(0)` never blocks, because this runs on the UI thread during an open and a blocking acquire would freeze the application for as long as somebody else kept the slide open. `LockStatus::Unavailable` is **not** a refusal to edit — advisory means cooperative, a workspace that cannot hold a lock file is the state this application ran in until today, and that folder will refuse the save too. And the stale time is **four hours**: Qt detects a dead owner immediately when the lock names *this* host, whatever the value, so this number only governs a lock taken by another machine over a share where no process can be interrogated — long enough not to expire mid-session, short enough that a remote crash does not cost a working day, with deleting the `.lock` file as the documented recovery. One side effect is recorded because the repository header used to promise the opposite: **the `annotations/` folder is now created on the first lock**, not only on the first save, since a lock file cannot live in a folder that does not exist and the scene most worth locking is the one nobody has annotated yet. 19 tests — infra's drive two repositories over one temporary directory, which works because `QLockFile` cannot tell a second lock in this process from one in another. Sixteen manual checks were run 2026-10-21 — group AE, **16 of 16 pass**, recorded in `docs/superpowers/specs/2026-10-20-annotation-file-locking-design.md` §6. AE16 needs a lock that is stale but not detectably dead, which only another host can leave, so it was run with a hand-planted lock naming one. **The run found one defect outside the checks, fixed the same day:** Preferences — and Open Annotations Folder, the Export Counts start folder and the save-failure folder picker — read the workspace from the `QSettings` value every instance shares, not the root this instance is using, so after one instance switched folders the other's Preferences showed a folder it was not in, and an OK without edits would have switched it there. **`AnnotationSettings` now holds its instance's workspace**, read once at construction and changed only by its own `setWorkspaceDirectory()`, which still writes the store so the next launch reads the last choice. Keep it that way: the store is shared and the repository root it mirrors is not, so a getter that re-reads the store is a getter for some other window's folder.
- **A selection always names an annotation the model holds.** `AnnotationModel::setSelected` refuses an id it cannot find, the empty id excepted — that is how a selection is cleared. A selection naming nothing paints no handles and matches no delete, and the model is the only place that can tell.
- **`AnnotationType` is derived from the geometry**, never stored beside it. `Annotation::type()` delegates to `core::typeOf()`, and the annotation-level `"type"` field in a saved file is written from the geometry and ignored on read. The two cannot disagree.
- **The painted interior and the hit-tested interior must match.** `core::hitTest` uses even-odd ray casting; `paintAnnotations` sets `Qt::OddEvenFill`. A self-intersecting trace is valid data — pathologists produce them — and these two must agree about which parts of one are inside.
- **A pending multi-click shape is not an annotation.** It lives in `ViewportWidget::Impl::pending`, never reaches `AnnotationModel`, and is therefore never saved. It is discarded on slide close and on a tool change, and survives focus loss — **observed 2026-10-12** (check P5): another window stole focus mid-trace and the preview came back identical.
- **The drawing tool and the serializer must agree on what a valid shape is.** `ui::pendingShapeCommits` reads `core::kMinPolygonVertices` and `core::kMinPolylineVertices` — the same constants the serializer enforces on both read and write. A tool that could commit a shape the serializer would refuse would produce work that cannot be saved.
- **A double-click closing a multi-click shape keeps its vertex.** Qt delivers `MouseButtonDblClick` in place of the second press, not in addition to it, so the pair places exactly one vertex. `ViewportWidget::mouseDoubleClickEvent` must not remove one: on a triangle that would fall below the minimum and discard the shape silently. The same rule holds for any close gesture: one that cannot reach the vertex minimum does not close and does not discard — it leaves the trace alive, and `commitPendingShape` makes that test before it destroys anything. **But the vertex it keeps must not duplicate the previous one.** The cursor has usually not moved since the last trailed point — the user stopped to double-click — so the click placed a vertex exactly on top of it. That zero-length segment paints nothing and measures nothing, but it makes the segments on either side share an endpoint, and `core::isSelfIntersecting` only excludes segments adjacent *by index*. The finished polygon then read as self-intersecting and its **area was withheld**, on roughly half of all hand-traced shapes, until 2026-10-17. Two guards now: `ui::shouldPlaceClickVertex` refuses the coincident click, and `core::outline()` drops consecutive duplicates so annotations already on disk measure correctly without being rewritten.
- **Tile caching** uses LRU with a CPU budget and priority-based prefetching.
- **Colour management** via SlideIO's transformer, with a global default profile and per-slide overrides.

- **Annotation persistence** in JSON with schema versioning (`schemaVersion` 1; a higher version is refused outright rather than partially loaded).
- **Auto-save** debounced at 2s with a 30s backstop. The decision is the pure `core::shouldAutosave`, because no test suite creates a `QCoreApplication` and a `QTimer` never fires in a test — the timer is a dumb clock that asks it.
- **Undo/redo** per slide via the command pattern, 50 steps
  (`app::UndoRedoStack`, `app::AnnotationEditCommand`). One command type covers
  create, delete and move, because the inverse is the same shape in all three:
  the state before and the state after. Single property edits fit it unchanged.
  **A second type, `AnnotationRetagCommand`, covers the one case it cannot:
  many annotations in one step.** `AnnotationEditCommand` is one annotation by
  construction and carries the index the annotation sat at
  (`AnnotationEditCommand.h:59`), because restoring a created or deleted
  annotation at the wrong position changes which shape paints on top and which
  one a click finds; a retag changes a property in place and moves nothing. It
  restores through `AnnotationModel::restoreMany`, which emits a dedicated
  `annotationsBulkChanged` signal and **deliberately not `modelReset`**
  (`AnnotationModel.h:145-150`): `MainWindow` connects `modelReset` to a lambda
  that clears the undo stack (`MainWindow.cpp:1295`), so a retag's own undo
  would destroy the command mid-call and wipe the user's history, and
  `AnnotationPersistenceService` deliberately does not connect `modelReset`
  (`AnnotationPersistenceService.cpp:43-46`), so a retag would never have been
  autosaved. The list and properties panels connect the new signal beside
  `modelReset` and rebuild once, not once per annotation. Commands are recorded
  *after* the model
  has already been changed through its own API, so `execute()` runs only on
  redo. The stack is cleared when the model is emptied for a different slide or
  scene — but not when the same scene is reopened for a colour-profile change,
  where the annotations come back under the same ids. Ctrl+Z during a live
  multi-click trace removes the last vertex instead, which is why the Undo
  action must stay enabled while tracing: a disabled `QAction` is removed from
  Qt's shortcut map and its key never fires. A menu action's shortcut is
  window-scoped and Qt matches it *before* the focus widget sees the key, so
  the Edit actions hand Ctrl+Z and Ctrl+Y to a focused text editor first —
  without that, typing in a dock's filter box and pressing Ctrl+Z would undo an
  annotation edit and autosave would write it.
